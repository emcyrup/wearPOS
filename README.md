# wearPOS

アパレル向けの **顧客管理 (CRM) / 在庫管理 / 売上分析** アプリです。
既存の POS レジとは連携 API で接続し、レジで発生した取引を取り込んで在庫・顧客実績・ポイント・LINE 通知まで自動で反映します。

カラー × サイズの SKU 管理と、シーズン (2026SS など) を軸にした値下げ・消化率の把握を中心に据えています。

## 機能

### 商品 / SKU 管理
- **商品登録**: 品番・価格・シーズン等を入力し、カラー × サイズを選ぶと全組み合わせの SKU を
  一括作成。JAN コード (EAN-13) の自動採番と店舗ごとの初期在庫まで同時に登録し、
  そのまま値札ラベル (バーコード) を印刷できます（管理者のみ）
- 品番 (スタイル) の配下にカラー × サイズのバリエーションを SKU として保持
- カラー × サイズの在庫マトリクス表示（上段: 在庫 / 下段: 累計販売）
- シーズンごとのプロパー / セール判定、値下げ率と価格改定履歴
- 消化率・プロパー消化率・粗利率の算出
- **SKU コードの変更**: 商品詳細の SKU 一覧からその場で変更（管理者のみ・重複チェックあり。
  取引明細や在庫は内部 ID で紐づくため過去の履歴は保たれます）

### 在庫管理
- SKU 単位の在庫と発注点（安全在庫）。※現在は単店舗運用のため店舗の選択・表示は
  隠しています（データモデルは複数店舗対応のまま。`lib/config.ts` の `MULTI_STORE` で復帰可）
- 入荷 / 在庫調整 / 棚卸の登録。棚卸は実棚数で上書き、それ以外は差分で増減
- すべての在庫変動を `StockMovement` に履歴として記録（変動後残数のスナップショット付き）
- 安全在庫割れのアラート

### 顧客管理 (CRM)
- 会員番号・氏名カナ・連絡先・担当店舗・好みタグ・接客メモ
- 累計購入額に応じた会員ランク（レギュラー / シルバー / ゴールド / プラチナ）とポイント付与率の自動判定
- ポイントの付与・利用・手動調整と、その残高履歴
- 購買履歴から **よく買うサイズ / カラー** を自動集計
- 休眠顧客（90日以上未来店）の抽出

### LINE 公式アカウント連携
- 店頭で6桁の連携コードを発行 → お客様がトークに送信 → 会員情報と LINE アカウントを紐付け
- **友だち追加からの新規会員登録**: 友だち追加すると登録フォームの URL が自動配信され、
  氏名・カナ・電話・メール・誕生日などを入力して送信すると、会員番号を自動で払い出して
  登録・LINE 連携まで完了（完了時にデジタル会員証もトークへ自動配信）
- 購入時にお買い上げ金額・獲得ポイント・残高を自動でプッシュ通知
- 「会員証」「ポイント」「履歴」などのキーワードに自動応答。お客様側から
  「通知オフ / 通知オン」でお知らせ配信の停止・再開、「連携解除」で LINE 連携の解除も可能
  （店側からも顧客詳細の「LINE 連携を解除」で解除できます）
- **デジタル会員証**: トークで「会員証」と送ると会員バーコードのリンクが届き、
  レジの会員照会でそのままスキャンできる（顧客詳細の「会員証を表示」からも確認可能）
- **再来店・おすすめ商品メッセージ**: 顧客詳細では購買傾向（よく買うサイズ・カラー）と
  在庫から「再来店の呼びかけ」「おすすめ商品の提案」の文面を自動作成し、編集して送信。
  顧客一覧の「LINE 一斉配信」では休眠会員などのセグメントに1通ずつ個別文面で一括送信できる
- **自動リマインド**: 設定 → リマインド設定で、経過日数などの条件による自動配信を
  ルールごとに ON/OFF（毎日 10:00 JST に Vercel Cron で実行）
  - お買い上げ後フォロー（購入7日後・着心地とお手入れのご案内）
  - 再来店のご案内（最終来店30日後・よく買うサイズ/カラーのおすすめ付き）
  - 休眠フォロー（最終来店90日・同じ方へは90日に1回まで）
  - 誕生日メッセージ（当日・年1回）
  - 経過日数は変更可能。二重送信は送信ログで自動防止
  - お客様ごとの個別設定: 顧客詳細の「このお客様へのリマインド設定」で
    ルール単位の ON/OFF と全停止を切り替えられる
- 顧客詳細から個別メッセージを送信、送受信ログを保存
- 友だち追加 / ブロック (unfollow) の状態を追跡

### 売上分析ダッシュボード
- 期間切替（7 / 30 / 90日）に加えて、カレンダーでの自由な期間指定と前同期間比較
- 純売上・客数・客単価・プロパー消化率・会員売上比
- 日別の売上と客数の推移
- カラー別 / サイズ別の販売構成、シーズン別売上、売れ筋 SKU、店舗別・スタッフ別実績
- **AI考察 (Claude × ChatGPT 討論)**: Claude の考察 → ChatGPT の検証 → Claude の結論、
  の討論を経て、回答を**【考察】（結論と打ち手）と【提案】（一歩先の取り組み）に分けて**
  コンパクトに表示（討論の経過は折りたたみ）。追加の質問での壁打ちも同じ形式で回答
  （`ANTHROPIC_API_KEY` 必須、`OPENAI_API_KEY` 未設定時は Claude 単独）

### 設定 / マスタ管理（管理者）
- **レジの支払方法**: 現金 / クレジット / 電子マネー / QR / その他に加えて、ギフト券・商品券・
  モール共通ポイントなどを**任意に追加・削除**できます。支払方法ごとに「レジに表示」
  「**分割決済に使える**」「お釣りを出せる」と表示順を設定でき、取引で使用済みのものは
  過去の伝票の表示を保つため削除ではなくレジ非表示に切り替わります
- **データの初期化**: 取引履歴 / 在庫と変動履歴 / 商品と SKU / 顧客とポイント / LINE ログを
  選んで一括削除できます（件数プレビュー + 確認フレーズ + 実行履歴の記録つき）。
  **既定では無効・グレーアウト**で、使うときだけ明示的に有効化する必要があり、
  1回実行すると自動的に無効へ戻ります

### ログインと権限
- ユーザー名 / パスワードでログイン。ユーザーが1人もいない状態では初期セットアップ画面から
  管理者アカウントを作成できます
- **ログイン画面から新規ユーザーを作成**して、そのままログインできます（「新規ユーザーを作成」タブ）。
  作成されるのは**スタッフ権限 + 既定機能（レジ・商品・在庫）**のみで、顧客情報・取引履歴・設定
  にはアクセスできません。管理者は 設定 → 「ログイン画面での新規ユーザー作成」で
  **だれでも作成可 / 合言葉が必要 / 作成させない** を切り替えられます（合言葉はハッシュ化して保存）
- **管理者**は全機能、**スタッフ**は許可された機能（レジのみ、在庫のみ等）だけ表示・アクセス可能。
  権限のないページはナビに出ず、URL 直打ちでもリダイレクトされます
- ユーザーの追加・権限変更・パスワードリセットは 設定 → ユーザーと権限（管理者のみ）
- デモデータのアカウント: `admin` / `admin1234`（管理者）、`staff` / `staff1234`
  （スタッフ: レジ・商品・在庫のみ）
- ダッシュボードは「表示項目」からユーザーごとに表示セクションをカスタマイズできます
- 全画面がスマートフォン・タブレットに対応（表は横スクロール、レジはタブレットで2カラム。
  スマートフォンでは入力欄を 16px にして iOS の勝手なズームを防止）

### レジ（店頭会計）
- レジページ（`/register`）は**ログインなしで使えます**（店頭のレジ端末でそのまま開ける）。
  ナビの「レジ」は**サイドメニューなしの専用ウィンドウ**で開き、すでにレジのウィンドウが
  開いていればリロードせずそのウィンドウをアクティブにします（会計中のカートが守られます）。
  担当者は選択のほか、**スタッフ名札バーコードのスキャン**でもセット可能
  （名札は 設定 → スタッフ → 「名札バーコード」から印刷）
- バーコードスキャン（カメラ / USB・Bluetooth リーダー / 手入力）→ カート → 会計までを完結
- バーコードが読み取れないときは、商品名・品番・カラーでの**商品検索**（店舗在庫つき）と、
  氏名・カナ・電話番号での**会員検索**から選んで追加・紐付けできます
- 商品登録されていないものは**「未登録商品を手入力で追加」**で商品名と価格を直接入力して
  会計できます（在庫は動かさず、レシート・伝票には入力した商品名が印字されます）
- **明細単位の値引き**と**伝票値引き**の両方に対応。どちらも**金額（¥）と割合（%）を
  併用**でき、合算した額（上限は明細金額 / 小計）が値引きされます
- 会員番号の照会・ポイント利用・支払方法（設定で追加・削除できます。既定は
  現金 / クレジット / 電子マネー / QR / その他。ギフト券などを追加可能）
- **分割決済**: 1回の会計で複数の支払方法を併用できます（例: 現金1万円 + 残りを電子マネー）。
  手段ボタンで残額が自動入力され、内訳の合計が支払額と一致するまで会計できません。
  現金など「お釣りを出せる」手段は行ごとに預かり金とお釣りを記録します。
  支払の内訳は `SalePayment` に保存し、レシート・伝票詳細・支払方法別の集計に反映されます
- **担当スタッフの選択が必須**（未選択では会計できません）
- 現金はお預かり金額の入力が必須（不足時は会計不可・不足額を表示）、その他の決済は
  決済端末での完了を確認するダイアログを経てから会計を確定
- 会計は POS 連携 API と同じ取り込みロジックを通るため、在庫減算・顧客実績・ランク・
  ポイント付与・LINE 購入通知まで即時反映
- 会計後の「レシートを印刷」は、**サイドメニューのない別ウィンドウ**でレシート
  （58mm 想定・伝票番号バーコード付き）を開いて印刷。過去の伝票の「レシート印刷」も同じ
  別ウィンドウで再発行可能
- **返品（取引の取消）**: 伝票詳細の「返品する」で返品伝票（`元伝票番号-R`）を作成し、
  在庫の戻し入れ・利用ポイントの返還・獲得ポイントの取消・累計購入額 / ランク / 来店回数の
  巻き戻しまで一括で実行（元伝票は書き換えず、二重返品は不可）

### バーコード
- SKU ごとの JAN コード（EAN-13）バーコードを SVG で生成し、値札ラベルとして印刷
  （商品詳細 → 「値札を印刷」。JAN が無い SKU は Code128 で SKU を符号化）
- JAN の採番ルールは「**年月 + 連番5桁**」（`490` + ユーザーが指定した年月 YYMM + 自動連番
  5桁 + チェックデジットの EAN-13）。年月は**数字6桁（例: 202608）で直接入力**でき、
  📅 ボタンからカレンダー（月ピッカー）でも選べます。連番は年月ごとに 00001 から自動払い出し
- **既存バーコードの読み取り登録**: 商品登録時に「自動採番 / 既存のバーコードを読み取って登録 /
  あとで設定」を選べます。メーカーが上代を明示した値札や、自店で過去に発行したラベルを
  そのまま SKU に紐づけられるため、値札の付け替えが不要です（重複チェックあり）。
  商品詳細の SKU 一覧からも1件ずつ登録・変更でき、レジで未登録バーコードを読み取ったときは
  そのコードを持ったまま商品登録画面を開けます
- バーコードスキャンは商品一覧の検索欄に組み込み。読み取った JAN / SKU で
  そのまま一覧を絞り込めます（JAN でのキーワード検索にも対応）
- **商品の基本情報に表示する項目そのものもカスタマイズ可能**（設定 → 商品の基本情報 項目）。
  項目を選択すると**名称・表示/非表示・選択肢・表示順 (↑↓)・削除をまとめて編集**できます。
  ブランド / カテゴリ / シーズンは選択肢としてマスタをその場で追加・削除でき、
  素材・原産国・取扱いと「フィット」「柄」などのカスタム項目には自由な**選択肢**を
  登録できます（登録するとドロップダウン、空なら自由入力。カラー・サイズは常に表示）
- 顧客一覧・商品一覧は**行のどこをクリックしても詳細ページへ遷移**します

## セットアップ

```bash
npm install
cp .env.example .env     # 必要に応じて値を編集
docker compose up -d     # ローカル用の PostgreSQL を起動
npm run db:migrate       # マイグレーションを適用
npm run db:seed          # デモデータ (3店舗 / 140SKU / 180日分の取引) を投入
npm run dev              # http://localhost:3000
```

デモデータを入れ直すだけなら `npm run db:seed` を再実行します（全件削除して作り直します）。
スキーマごと作り直す場合は `npm run db:reset`（**データベースの中身を完全に削除します。本番では実行しないでください**）。

## Vercel + Neon へのデプロイ

アプリを実際に動かす（動的配信）場合は、**[DEPLOY.md](./DEPLOY.md) に詳しい手順**があります。
Neon でのデータベース作成、Vercel へのインポート、環境変数、デモデータ投入、LINE 連携の設定、
トラブルシューティングまでを順に説明しています。

概要だけ示すと次のとおりです。

1. [Neon](https://neon.tech) で PostgreSQL を作り、**Pooled**（`-pooler` 入り）と **Direct** の
   接続文字列を控える
2. [Vercel](https://vercel.com) にリポジトリを Import し、環境変数を設定してからデプロイ
3. 手元から本番 DB に対して `DATABASE_URL="<Direct 接続文字列>" npm run db:seed`

`vercel-build` スクリプトが `prisma migrate deploy` を実行するため、テーブル作成は自動です。

### アクセス制御について

画面はログイン必須（ロール別の機能制限つき）、POS 連携 API は API キー、LINE Webhook は署名で
保護しています。お客様向けのページ（会員証・会員登録フォーム・ポイント）はログイン不要ですが、
LINE ユーザーごとの署名トークンでしか開けません。**レジとレシート印刷ページは店頭端末で
使うためログイン不要**にしています（店内ネットワークからのみ開ける構成を推奨します）。

本番運用では `AUTH_SECRET` にランダム値を設定し、デモ用アカウント（`admin` / `admin1234` など）の
パスワードを必ず変更してください。

## GitHub Pages での画面デモ公開

`docs/index.html` に、全画面をデータ入りで確認できる静的デモを生成済みです。
リポジトリの **Settings → Pages** で以下を選ぶと公開されます。

| 項目 | 値 |
| --- | --- |
| Source | Deploy from a branch |
| Branch | `main`（デモを置いたブランチ） |
| Folder | `/docs` |

公開 URL は `https://<ユーザー名>.github.io/wearPOS/` です。

画面やデモデータを変更したあとは、次のコマンドで再生成します。

```bash
npm run db:seed       # デモデータを作り直す場合のみ
npm run demo:build    # ビルド → 各画面を取り込み → docs/index.html を出力
```

`npm run demo:build` はアプリを一時的に起動し、ブラウザで描画された状態の HTML と CSS を
1 枚のページにまとめます。グラフも SVG として保持されるため、画像ではなく実際の描画が残ります。

**デモの制約**: GitHub Pages は静的ファイルのみを配信するため、サーバー処理は動きません。
画面デザインとデータ表示は本物ですが、絞り込み・在庫登録・LINE 送信・POS 連携 API は動作しません
（画面間のリンクとタブ切り替えのみ有効です）。実際に操作する場合は `npm run dev` で起動してください。

### 環境変数

| 変数 | 用途 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL の接続文字列。Neon ではプール付き (`-pooler`) を指定 |
| `DIRECT_DATABASE_URL` | マイグレーション用の直結の接続文字列（Neon などプールを使う場合に必要）|
| `DATABASE_POOL_MAX` | 1インスタンスあたりの最大接続数（省略時 5）|
| `POS_API_KEY` | POS 連携 API の共有シークレット。未設定だと API は 503 を返します |
| `LINE_CHANNEL_SECRET` | LINE Webhook の署名検証に使用 |
| `LINE_CHANNEL_ACCESS_TOKEN` | LINE へのメッセージ送信に使用 |
| `LINE_PUSH_ENABLED` | `false` で LINE への送信を停止（送信ログのみ記録）|
| `ANTHROPIC_API_KEY` | ダッシュボードの AI考察 (壁打ち) に使用。未設定だと考察機能のみ使えません |
| `OPENAI_API_KEY` | AI考察の討論相手 (ChatGPT)。未設定なら Claude 単独の考察になる |
| `AUTH_SECRET` | ログインセッションの署名鍵。本番では必ずランダム値を設定（未設定時は `POS_API_KEY` から導出）|
| `AUTH_DISABLED` | `1` でログインを無効化（静的デモ生成・ローカル確認用）|
| `CRON_SECRET` | リマインド実行 API (`/api/reminders/run`) の認証。Vercel Cron が自動で付与（`POS_API_KEY` でも実行可）|
| `LIFF_ID` / `LIFF_CHANNEL_ID` | リッチメニューをタップで直接画面遷移にする場合に設定（未設定ならキーワード送信方式）|
| `APP_URL` | LINE で送る会員証リンクの基点 URL（未設定ならアクセス時のホスト名から自動判定）|

LINE の認証情報が未設定でもアプリは動作します。その場合、送信はスキップされログだけが残るため、
連携前の画面確認や開発中の動作確認に使えます。

## POS レジ連携 API

すべてのエンドポイントで `X-API-Key: <POS_API_KEY>` ヘッダ（または `Authorization: Bearer`）が必要です。

### 取引の取り込み

```
POST /api/pos/sales
```

```json
{
  "externalId": "POS-SHIBUYA-000123",
  "storeCode": "SHIBUYA",
  "staffCode": "S002",
  "memberCode": "M10001",
  "soldAt": "2026-07-29T14:32:00+09:00",
  "type": "SALE",
  "paymentMethod": "CREDIT",
  "pointsUsed": 1000,
  "lines": [
    { "sku": "26SS-SH-001-BLK-M", "quantity": 2, "unitPrice": 12800 },
    { "barcode": "4912345678", "quantity": 1, "unitPrice": 12800, "discount": 800 }
  ]
}
```

1リクエストで行われる処理:

1. 伝票と明細を作成
2. 該当店舗の在庫を減算し、在庫変動履歴を記録（`type: "RETURN"` なら加算）
3. 顧客の累計購入額・来店回数・会員ランクを更新
4. ポイントを利用分だけ減算し、正味支払額に対して付与
5. LINE 連携済みならお買い上げ通知をプッシュ

1〜4 は単一トランザクションで実行されます。LINE 送信は外部 API 呼び出しのためトランザクション外で行い、
送信失敗が取引の記録に影響しないようにしています。

**冪等性**: `externalId` が既に存在する場合は何も行わず `duplicated: true` を返します。
通信エラーやタイムアウト時は、同じペイロードをそのまま再送して構いません。

複数取引をまとめて送る場合は `{ "sales": [ ... ] }` 形式（1回あたり最大200件）。
一部が失敗しても成功分は取り込まれ、`errors` に失敗した要素の添字と理由が返ります。

### 照会系

```
GET  /api/pos/products?season=2026SS&updatedSince=2026-07-01T00:00:00Z
GET  /api/pos/inventory?storeCode=SHIBUYA&sku=26SS-SH-001-BLK-M
GET  /api/pos/customers?memberCode=M10001
POST /api/pos/customers        # レジでの新規会員登録
```

`/api/pos/inventory` は `storeCode` を省略すると全店舗の在庫を返すため、他店在庫の取り寄せ判断に使えます。

## LINE Webhook

LINE Developers コンソールに以下を登録します。

```
POST /api/line/webhook
```

`X-Line-Signature` を生のリクエストボディに対して検証し、不一致なら 401 で拒否します。
個々のイベント処理が失敗しても LINE 側の再送を招かないよう、全体としては 200 を返します。

## 技術構成

- **Next.js 15** (App Router / Server Components / Server Actions)
- **Prisma 7** + PostgreSQL（`prisma.config.ts` + pg ドライバアダプタ構成）
- **Tailwind CSS v4**
- **Recharts** — ダッシュボードのグラフ
- **Zod** — API とフォームの入力検証

データベース接続はモジュール読み込み時ではなく初回利用時に作られるため、
`DATABASE_URL` が無い環境でも `next build` は通ります。

## 補足

- 会計はアプリ内のレジ画面（`/register`）でも、既存 POS からの連携 API 経由でも行えます。
  どちらも同じ取り込みロジックを通るため、在庫・顧客実績・ポイントの反映は同一です。
- ポイントは「ポイント利用分を差し引いた正味の支払額」に対して付与され、二重取りを防いでいます。
- 消費税は品番ごとの税率を明細金額で加重平均して算出しています（軽減税率の混在に対応）。
